## Major

### [Major] R1 refreshStore adopts the server's demo store fallback, `src/stores/auth.ts:163`
**Problem**: `refreshStore` takes whatever row `/api/query` returns for `stores` and puts it into `useAuth.store` and Dexie. It never checks that `fresh.id === storeId`. The server answers a `stores` select with a hard coded demo store and no error whenever Postgres is unreachable (`server/index.js:2667`, `demoStore = { id: 'store-default-001', name: 'Toko Aplikasi Kasir', tax_rate: 10, ... }`). `requireUser` also falls back to a fake admin on the same failure (`server/index.js:3482`), so the request does not fail earlier.
**Failure scenario**: cashier tablet is open on POS, production store has tax 0%. Supabase refuses connections for a minute (53300 too many connections, ECONNRESET, pooler restart). The 60 second poll in `src/App.tsx:64` gets the demo store back. `JSON.stringify(current) !== JSON.stringify(fresh)`, so `set({ store: fresh })` runs. `OrderPanel` now reads `tax_rate = 10`, `taxInclusive` undefined and `taxDefaultOn` undefined, so the tax checkbox appears checked and every order placed adds 10% on top of the total. Receipts print "Toko Aplikasi Kasir" without logo. The orders are queued offline and sync later with the wrong tax and total. Before this diff the store was only fetched at login, so a running POS kept the correct settings during an outage.
**Why it matters**: the POS is offline first and is expected to keep selling during a database outage. With the poll, an outage silently changes the price the customer pays and writes wrong tax into orders on every open device. A stray `store-default-001` row also stays in `db.stores`.
**Suggested fix**: in `refreshStore`, ignore a response whose `id` differs from the requested `storeId`. Also re-check after the await that `get().store === current` and `get().sessionStoreId` is unchanged before calling `set`, so a slow response cannot overwrite a store that was saved or signed out in the meantime. Add a unit test for both guards.

### [Major] R2 Shipping label prints the account name instead of the recipient typed at checkout, `src/lib/receipt.ts:307`
**Problem**: `shippingTarget` builds the name as `customer?.name || order.customer_name || 'Penerima'`. For storefront orders `orders.customer_name` is the "Nama Penerima" field of the checkout form (`src/pages/public/PublicCheckout.tsx:382`, server message "Nama penerima wajib diisi" at `server/index.js:1946`) and `customer_id` is the buyer account. The phone uses the opposite priority (`order.customer_phone || customer.phone`), so the label mixes the account name with the order phone and order address.
**Failure scenario**: account "Budi Santoso" checks out and changes Nama Penerima to "Bengkel Jaya Motor" with the workshop address. The order stores `customer_name = 'Bengkel Jaya Motor'`. Staff open the order in Riwayat and print the label. If Budi is in the local customer cache the label reads "Budi Santoso" above the workshop address. If the customer row is not cached yet (Riwayat never pulls customers) the same order prints "Bengkel Jaya Motor". The result depends on cache state.
**Why it matters**: item 16 exists to label the destination. A package with the wrong recipient name at an office, workshop, or apartment desk gets refused or misrouted. The unit test `shippingLabel.test.ts:60` locks in the wrong priority and never covers an order where both names exist and differ.
**Suggested fix**: when the address comes from the order (`delivery_address` set), take name and phone from the order first and fall back to the customer. Keep the customer first order only for the fallback path that uses the customer's main address. Add a test with `customer_name` different from `customer.name`.

## Minor (appended as confirmed, final order set at the end)

### [Minor] Pixel ID guards have no test that can fail, `server/index.js:3044` and `src/lib/pixelToko.ts:51`
**Problem**: `periksaIdPixel` (server) and `idPixelDariToko` (client) are the two guards between a stored value and a third party script URL. Neither has a unit test. `scripts/verify_pixel_toko.cjs:106` only types `GA-123` into the Settings form, which is rejected by the client side check in `Settings.tsx:308` before any request is sent.
**Failure scenario**: someone removes `periksaIdPixel` from `validatePatchForUpdate`, or loosens a pattern in `idPixelDariToko`. All 22 assertions of the pixel suite and all vitest files still pass.
**Suggested fix**: add a vitest file for `idPixelDariToko` (invalid stored values become null). Move `POLA_ID_PIXEL` and `periksaIdPixel` into a module that can be imported without starting the server (same approach as `server/pgErrors.js`) and test it. Add one E2E assertion that posts an invalid ID straight to `/api/query` and expects 400.

### [Minor] Meta PageView is sent twice on every in store navigation, `src/lib/pixelToko.ts:185`
**Problem**: the Meta pixel listens to `history.pushState` by default and fires its own PageView on each history change (Meta developer blog "Tagging Single Page Applications with the Facebook Pixel", flag `fbq.disablePushState`). The app router uses `pushState` (`src/lib/router.tsx:57`) and `PublicShell` also calls `lacakHalaman()` on every route change.
**Failure scenario**: buyer opens /toko, then a product, then the cart. Meta receives 1 PageView for the landing page and 2 for each of the next two pages, 5 instead of 3. The Playwright suite replaces `fbevents.js` with an empty body and asserts `>= 1`, so it cannot see this. Not executed here, based on Meta's documented behavior.
**Suggested fix**: set `fbq.disablePushState = true` before `fbq('init')` in `pasangMeta`, since the app already sends page views itself.

### [Minor] Dirty form merge drops "Pajak tercentang otomatis" when it is switched off for the first time, `src/pages/Settings.tsx:1459`
**Problem**: `gabungPerubahanLuar` treats an unset feature flag as off (`fiturForm[k] ?? false` against `fiturAwal[k] ?? false`). For `taxDefaultOn` unset means on (`industries.ts:31`, `OrderPanel.tsx:55`).
**Failure scenario**: store has never saved `taxDefaultOn`. Admin switches "Pajak tercentang otomatis" off and keeps editing. Another device changes any store setting, the 60 second refresh delivers it, and the merge runs. `false ?? false` equals `undefined ?? false`, so the admin's change is not seen as a change and the merged form takes the server value (unset, meaning on). The switch flips back to on without notice. If that was the only edit, the Save bar also disappears.
**Suggested fix**: compare with the real default per flag, for example reuse the normalisation of `shallowEqualForm` (`taxDefaultOn !== false`), or resolve `taxDefaultOn` to an explicit boolean in `resolveFeatures`. Extract the merge to a tested module, it is private to the page and has no unit test.

### [Minor] Duplikat ignores product sets for stock and cost, `src/pages/Orders.tsx:479`
**Problem**: the stock warning reads the product's own `stock_qty`, and the cart line takes the product's stored `cost_price`. For a product set POS uses the component stock (`Menu.tsx:253`) and the live component cost (`Menu.tsx:270`, `modalSetSaatIni`).
**Failure scenario**: order contains set "SET-CRF-RED" qty 2, components in stock for 15 sets, the set row itself has `stock_qty = 0`. Duplikat shows "1 barang stoknya kurang dari jumlah pesanan asal: SET-CRF-RED (stok 0, pesanan 2)" although the set can be assembled. The duplicated line also stores the set's saved cost, not the current component cost, so profit for the copy differs from the same sale entered in POS.
**Suggested fix**: share one helper with `Menu.tsx` for availability and cost of a product (set aware) and use it in `duplikatPesanan`.

### [Minor] Store poll downloads the whole store row every minute, `src/stores/auth.ts:169`
**Problem**: `refreshStore` runs `select('*')` on `stores` every 60 seconds per visible window and on every focus. The row holds four base64 images: logo and signature up to 600px, QRIS up to 900px, PDP banner up to 1200px (`Settings.tsx:254`, `266`, `895`, `937`).
**Failure scenario**: store with all four images set has a row of several hundred KB. One cashier tablet open 12 hours makes about 720 polls, a few hundred MB of transfer per device per day, plus two `JSON.stringify` passes over the row each minute.
**Suggested fix**: select only the columns POS needs (`tax_rate`, `features`, `currency`, `name`, receipt fields, `points_per_amount`) and merge them into the current store, or compare a cheap version field first.

### [Minor] HPP silently drops costs once the store has more than 1000 expenses, `src/lib/sync.ts:258`
**Problem**: HPP per barang and "HPP penuh" read follow up costs from the local `expenses` table. `pullExpenses` keeps only the 1000 newest rows by `expense_date`.
**Failure scenario**: store reaches 1400 expenses. A nota from last year has two follow up costs dated before the 1000 row window. Its detail shows "Belum ada biaya yang menempel" or only the two form costs, and products whose latest received nota is that one show no "HPP penuh". No message says that data is missing.
**Suggested fix**: load nota costs with their own query (`purchase_id` in the pulled nota ids, or `purchase_id is not null`) instead of relying on the newest 1000 rows.

### [Minor] HPP visibility uses a raw role check, `src/pages/Purchases.tsx:232` and `src/pages/Products.tsx:206`
**Problem**: both pages use `profile?.role === 'admin'`. The rest of the app uses `hasCapability`, which maps the legacy role `manager` to admin (`src/lib/roles.ts:133`, server `effectiveRole`).
**Failure scenario**: a profile with role `manager` can open Pengeluaran and attach a cost to a nota (`Expenses.tsx:91` uses `hasCapability`), but the nota detail shows no "HPP per barang" and Produk shows no "HPP penuh".
**Suggested fix**: gate with `hasCapability(role, 'manageExpenses') && hasCapability(role, 'managePurchasing')`.

### [Minor] Label button is missing when the customer is not in the local cache, `src/pages/Orders.tsx:288`
**Problem**: the fallback to the customer's main address needs the customer row in Dexie. Riwayat pulls orders every 20 seconds but never pulls customers.
**Failure scenario**: cashier tablet creates customer "Bengkel Aldo" with an address and records a WhatsApp order. The packing PC has Riwayat open since morning. The order appears with customer "—" and no "Cetak Label Kirim" button until someone opens Dashboard, Kasir, or Customers on that PC.
**Suggested fix**: pull customers on Riwayat mount and when an order references an unknown `customer_id`, or fetch that one customer when the detail opens.

### [Minor] E2E check for the copied tax choice passes without the feature, `scripts/verify_duplikat_transaksi.cjs:156`
**Problem**: the source order has tax and the store default is "tax on", so `#cek-pajak` is checked and `(o.tax > 0)` is true even if `taxEnabled` is never copied. The two tempo orders without tax are only used for the due date.
**Failure scenario**: remove `taxEnabled: Number(o.tax ?? 0) > 0` from `Orders.tsx:531`. The suite still reports all assertions green.
**Suggested fix**: duplicate an order with `tax = 0` while the store default is on and assert the checkbox is unchecked and the saved copy has `tax = 0`.

### [Minor] verify_duplikat_transaksi leaves the store tax rate at 10, `scripts/verify_duplikat_transaksi.cjs:46`
**Problem**: the suite runs `update public.stores set tax_rate = 10` and the `finally` block never restores the old value. `verify_pajak_per_transaksi.cjs` restores it, this one does not.
**Failure scenario**: local store has tax 0 like production. After one run every later suite and every manual session runs with 10% tax, and `verify_permintaan_client.cjs` item 14a flips from "checkbox hidden" to "checkbox shown".
**Suggested fix**: read the rate before the update and restore it in `finally`.
